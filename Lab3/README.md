# Lab3 — IoT Botnet Traffic Classifier

An end-to-end Machine Learning web application that classifies network
flows as **Safe** or a **Threat** (DDoS / botnet traffic), built for the
"Building Interactive Threat Detection Systems" team-project lab (Topic 4:
IoT Botnet Traffic Classifier).

## What's included

| Deliverable | Where |
|---|---|
| Data & model pipeline (cleaning, feature engineering, training) | `src/data_loader.py`, `src/preprocessing.py`, `src/train.py` |
| Same pipeline + evasion test, as a notebook | `IoT_Botnet_Traffic_Classifier.ipynb` |
| Trained, serialized model | `models/iot_botnet_model.pkl` (generated by `train.py`, not committed) |

## Dataset — and an important note on where it came from

**Goal for this topic:** detect DDoS/botnet traffic using network flow
statistics (packet size, flow duration, byte counts).

The assignment's suggested datasets for this topic (N-BaIoT, Bot-IoT) are
normally obtained from the UCI Machine Learning Repository or Kaggle. **This
project's development sandbox has no outbound network access to either** —
only a small allowlist of hosts (GitHub among them) is reachable. Rather
than fabricate data, this project uses a real public dataset that *is*
reachable and satisfies the same technical requirements:

**[CICIDS2017](https://www.unb.ca/cic/datasets/ids-2017.html)** (Canadian
Institute for Cybersecurity), specifically the **Friday-Afternoon DDoS**
capture — `Friday-WorkingHours-Afternoon-DDos.pcap_ISCX.csv`, mirrored on
GitHub at
[StarterArcher/CICIDS2017](https://github.com/StarterArcher/CICIDS2017).
Downloaded automatically on first run into `data/raw/` (not committed —
~36 MB).

- **225,745 real network flow records**, each pre-summarized by
  CICFlowMeter into exactly the feature family this topic calls for: flow
  duration, forward/backward packet counts, byte counts, packet-length
  min/max, byte/packet rates, and TCP flag counts.
- **Real, labeled DDoS attack traffic** (128,027 DDoS flows vs. 97,718
  BENIGN), not synthetic data — generated by an actual DDoS tool (LOIT)
  against a real target during the CIC's capture.
- It is *flow*-level data (one row per connection), not raw packets or
  device-specific IoT captures — the honest gap between this and N-BaIoT/
  Bot-IoT. **If you have Kaggle/UCI access for your actual submission**,
  swapping in real N-BaIoT or Bot-IoT data only requires pointing
  `src/config.py`'s `RAW_CSV_URL`/`RAW_CSV_PATH` at the new file and
  adjusting `config.DROP_COLUMNS`/`LABEL_COLUMN` to match its schema — the
  rest of the pipeline (cleaning → train → serialize → Streamlit) is
  dataset-agnostic.

## Method

- **Cleaning:** `Source IP`, `Source Port`, `Destination IP`,
  `Destination Port` and `Timestamp` are dropped before modelling — keeping
  them would let the model key off this one capture's specific hosts/ports
  (e.g. always flooding port 80) instead of learning general flow behavior,
  the same reasoning used for host-identifying fields in Labs 1 and 2.
  `Flow Bytes/s`/`Flow Packets/s` are `inf` whenever a flow's duration
  rounds to zero (a CICFlowMeter division-by-zero quirk); these and any
  other missing values are treated as missing and the row is dropped
  (4 rows, out of 225,745).
- **Target:** `is_threat` = 0 for `Label == "BENIGN"`, 1 for `Label ==
  "DDoS"`.
- **Model:** `RandomForestClassifier(n_estimators=200)`. No feature scaling
  is applied — tree splits compare raw values within one feature at a
  time, so they're scale-invariant, and skipping it keeps the deployed app
  simpler (one fewer artifact to keep in sync between training and
  inference).
- **Split:** stratified 70/30 train/test.
- **Serialization:** the fitted model, the exact feature-column list, and
  the held-out test metrics are bundled together with `joblib` into
  `models/iot_botnet_model.pkl`, so `app.py` reproduces identical
  preprocessing at inference time without retraining.

## Results (last run)

| Metric | Value |
|---|---|
| Accuracy | 0.9996 |
| Precision | 0.9998 |
| Recall | 0.9995 |
| F1-score | 0.9997 |

Confusion matrix: TN=29,308, FP=7, FN=18, TP=38,390.

This near-perfect score is expected, not a red flag: CICIDS2017's Friday
DDoS is a **volumetric flood** — its attack flows are statistically very
different from benign traffic (see feature importance below), so a Random
Forest separates them almost perfectly. That's exactly what makes the
evasion test below meaningful — the model is genuinely excellent at
catching *this* kind of attack, and the interesting question is what kind
of attack it *isn't* good at catching.

**Top features** (`outputs/feature_importance.png`): `Fwd Header Length`
and `Total Length of Fwd Packets` dominate, followed by `Total Fwd
Packets` and `Total Length of Bwd Packets`. This makes sense from a
networking perspective — a flood attack pushes far more packets and far
more total bytes through a connection than normal traffic does in the same
window, and header length scales directly with packet count. The model has
essentially learned "how much traffic moved through this connection," which
is the single strongest signal a volumetric DDoS leaves behind.

## Live Defense — the evasion test (Step 4)

**Attack case:** `data/low_and_slow_evasion.csv` — 40 hand-crafted flow
records simulating a **low-and-slow DDoS** (Slowloris-style): each one
holds a connection open for 60–180 seconds while trickling only 3–8 tiny
packets total, instead of moving a lot of data quickly. Generated by
`scripts/make_evasion_set.py`, with the exact reasoning documented at the
top of that file.

**Result: 40/40 evaded — 100% false negatives.** Every crafted row is
classified **Safe**, with predicted threat probability between 0.025 and
0.435 (all comfortably under the 0.5 decision threshold; the real DDoS test
flows the model *does* catch mostly score at or near 1.0).

**Why it works:** the model learned that "threat" looks like *a lot of
traffic moving through a connection* (§ feature importance above) — because
that's what every attack example in its training data actually looked
like. A low-and-slow attack is specifically engineered to avoid that
footprint: few packets, few bytes, spread across a long duration. Its flow
statistics land in a region of feature space the model has no attack
examples for at all, so it defaults to "this looks like quiet, idle
traffic" — a textbook false negative caused by **training-data blind spot**,
not a bug in the model or the code.

**How to improve it**, in order of effectiveness:
1. **Add rate/behavioral features that are only meaningful in aggregate**,
   e.g. concurrent-open-connections-per-source-IP or requests-per-source
   over a sliding time window. A single low-and-slow flow looks idle; a
   thousand of them from a coordinated botnet targeting one server, open
   simultaneously, is not — but that pattern is invisible at the
   single-flow level this model operates on (this is the same lesson Lab
   1's `masscan_tcp_syn` and Lab 2's unseen-attack-type false negatives
   both point at: a model can only be as good as what its per-record
   features can see).
2. **Retrain with labeled low-and-slow examples** once available (e.g. from
   a Slowloris-specific capture) so the forest gets at least some direct
   signal for this pattern, rather than relying on generalization from
   flood attacks alone.
3. **Add a duration-based rule layered on top of the model** as a stopgap —
   e.g. flag any connection open longer than N seconds with near-zero
   throughput for manual review — since this project's model currently has
   zero signal for "suspiciously long AND suspiciously quiet."

## Control-question prep (for the live presentation)

- **Why did the model fail on the low-and-slow input?** See "Why it works"
  above — the training data's only attack examples were high-volume floods,
  so the model has no learned signal for a low-volume, long-duration
  attack pattern.
- **How would you improve it?** See the three numbered options above;
  lead with the aggregate/behavioral-feature option, since it addresses
  the root cause (per-flow features fundamentally can't see multi-flow
  coordination) rather than papering over one specific attack shape.
- **Why Random Forest?** Recommended by the assignment; handles the mix of
  count/rate/flag features natively without scaling, resists overfitting
  better than a single Decision Tree, and `feature_importances_` gives a
  direct, presentable answer to "what is the model actually looking at."
